Chapter 03 · Inference

The Bill Arrives

No weights change in this chapter. The model is fixed, and the only question is how cheaply and quickly it can be run against a live request. Nearly every technique here exists because generating one token at a time is limited by memory rather than by arithmetic — a sentence that sounds technical and turns out to explain most of an API price list.

C.01 · The shape of a request

Every request has two halves with opposite bottlenecks

01
IraReading my question and writing your answer — those are the same job, surely.
02
EchoThey are opposite jobs. I read your nine words in one go. I have to write mine one at a time, and each one costs a complete pass over every weight I have.
03
IraEvery weight? For one word?
EchoAll hundred and forty gigabytes of them. Mostly I am waiting for memory, not calculating. That is why output tokens cost you several times more than input tokens.
04
Almost every line on an API price list follows from this split

Prefill processes the whole prompt in parallel, in one pass. There is plenty of arithmetic to do, so arithmetic is what limits it. Decode produces one token per pass over the entire model, with very little arithmetic each time, so the speed of moving weights out of memory is what limits it.

05
A consequence worth keeping

Different hardware suits each phase, which is why large providers now split prefill and decode across different machines.

C.01 · Vocabulary for reading benchmarks

The five numbers a serving engineer argues about

These terms appear throughout vendor material and rarely get defined. Two of them trade directly against each other, which is why a single headline figure for inference performance is usually not meaningful.

Time to first token

How long the user waits before anything appears. Set by prefill, so it grows with prompt length.

Time per output token

The gap between one token and the next once generation starts. Set by decode, and what makes a reply feel fast or laboured.

Throughput

Total tokens the whole system produces per second across all users. The operator’s measure, not yours.

Batch size

How many requests are being served together. Raising it raises throughput and worsens the wait for each individual user.

Goodput

Throughput counting only requests that met their latency target. The honest version of throughput.

The central trade-off

Throughput and latency are bought from each other

Packing more requests onto an accelerator uses it more fully and lowers cost per token, while making every individual user wait longer. Where a provider sets that dial is a commercial decision, and it is rarely disclosed.

When reading a performance claim

Ask at which batch size and which context length it was measured. A figure quoted without both is not comparable to anything, and a surprising number of published figures are quoted without both.

Definitions follow Austin et al., How To Scale Your Model, ch. 7; and ‘Large Language Model Inference Acceleration: A Comprehensive Hardware Perspective’, arXiv:2410.04466.

The one-line version

The cache converts a computation problem into a memory problem. Without it, generation would be far too slow to be usable. With it, the binding constraint on how many users a machine can serve becomes how much memory their conversations occupy.

What is stored

Two vectors per token, per layer, per attention head. Nothing about the words themselves; only intermediate arithmetic.

Who pays for it

Each concurrent request holds its own cache. Ten users with long documents need ten caches in accelerator memory at once.

Why policy readers should care

Context length is sold as a headline feature, and it is priced as one. It is a memory commitment rather than a software setting.

C.03 · Serving the cache efficiently

Three ideas, two of them borrowed from operating systems

01
IraWhy not just give each conversation the memory it needs?
02
EchoNobody knows how long a reply will be until it is finished. Early systems reserved room for the longest reply that might happen. Most replies are much shorter, so most of that expensive memory sat empty.
03
The fix was thirty years old and came from somewhere else

Operating systems solved this in the 1960s. Stop demanding that memory sit in one piece. Cut it into fixed-size blocks, scatter them anywhere, and keep a lookup table.

Paged attention
The mechanism

A lookup table maps each request’s sequence to scattered physical blocks, as virtual memory maps a program’s addresses to pages.

The reported gain

The original paper reported two to four times the throughput of the systems it replaced, at the same latency. That is the authors’ own measurement.

The status in 2026

Standard rather than optional. Every serious engine implements it, so it is a floor rather than an advantage.

W. Kwon et al., SOSP 2023, arXiv:2309.06180.
Timelines are schematic. Mechanism: G.-I. Yu et al., ‘Orca’, OSDI 2022; Kwon et al., arXiv:2309.06180; A. Agrawal et al., ‘Sarathi-Serve’, OSDI 2024.
C.03 · The one that appears on your bill

Prefix caching: charging less for text the system has already read

Many requests share a long opening: a system prompt, a policy document, a codebase, the earlier turns of a conversation. Prefill for that shared portion produces identical cache entries every time, so it can be computed once and reused.

Why this matters for agents

Agentic workloads are almost all shared prefix

An agent replays a growing transcript on every step. Without prefix caching the same history would be re-read dozens of times in a single task, and long agent runs would be commercially impossible. This one optimisation is a precondition for the entire category of product.

Mechanism builds on PagedAttention block sharing, arXiv:2309.06180. Commercial pricing structures vary by provider and should be read from current provider documentation rather than assumed.
C.04 · Spending less

Guess ahead, and only wake the part of the model you need

01
The problem

Decoding is slow because each token needs a full pass over a very large model, and that pass is mostly spent waiting for memory rather than calculating.

02
IraWhat if something small and fast guessed the next few words, and you just checked them?
03
EchoI can check four guesses in a single pass I was going to make anyway. Three were right. I regenerate the fourth.
04
The important part

Verification preserves the output distribution exactly. You get the same answer the large model would have produced alone, sooner. This is a pure engineering optimisation, not a quality trade.

It is a latency tool

It helps most when the accelerator is underused: small batches and interactive single-user workloads.

It is not a throughput tool

At large batch sizes the accelerator is already saturated, so speculation adds work without speed. Commonly disabled above a batch size in the low tens.

It changes nothing semantically

The rejected token is simply regenerated. Nobody, including the model, can tell the difference in the output.

Mechanism: Y. Leviathan et al., ‘Fast Inference from Transformers via Speculative Decoding’, arXiv:2211.17192. The batch-size guidance is drawn from vendor engineering guides, 2026, and is not independently reproduced.
C.04 · How to read a parameter count

Mixture of experts: most of the model sits out most of the time

In a mixture-of-experts model the feed-forward layers are split into many separate blocks, and a small router sends each token to only a few of them. Total parameters and active parameters therefore come apart — and almost every published headline figure quotes the former.

The practical consequence for compute assessments

Comparing a mixture-of-experts model against a dense model on total parameters alone will overstate the former’s compute requirement per token, and understate its memory requirement relative to its speed. Assessments of what hardware a model needs should state which quantity they use. A model can be cheap to run and still need a very large machine to hold it.

Mechanism and the batch-size arithmetic for serving: Austin et al., How To Scale Your Model, ch. 4, question 8, and ch. 7.
C.05 · Spending more, deliberately

Three ways to buy a better answer at the moment of asking

Mode 1
Sequential · think for longer
Let me check that. No, wrong. Try again from the third line.

The model writes a longer chain of working before answering, checking and correcting itself as it goes. This is the behaviour that emerged from verifiable-reward training in chapter 02.

Cost scales with the length of the chain, and the chain is billed even where it is hidden from you
Mode 2
Parallel · answer several times
try 1try 2try 3try 4

Sample many independent attempts and select among them, by majority vote, by a scoring model, or by running a verifier over each.

Cost scales with the number of attempts; latency need not, because they run at the same time
Mode 3
Iterative · use tools and revise

Search, run code, read a file, then revise the answer in the light of what came back. The loop may run many times.

Cost is unpredictable in advance, which is what makes agentic products hard to price
The common thread

Capability is no longer a fixed property of the released weights

It is a function of the weights and the compute budget allowed at answer time. The same weights can be run at low budget or at very high budget, with materially different capability, and the budget is set by whoever deploys the model rather than by whoever trained it.

Why this complicates governance

Evaluating a model no longer means evaluating a fixed artefact. Any threshold, evaluation or disclosure regime defined over the model alone leaves the compute budget unspecified. Chapter 04 works through what that does to the instruments currently in use.

Reported accuracy does improve with answer-time compute, though with diminishing returns and unevenly across task types.

Lambert, arXiv:2504.12501, ch. 7, ‘Reasoning and Inference-Time Scaling’; scaling curves for train-time and answer-time compute as published with OpenAI’s o1, and discussed in arXiv:2410.04466, sec. 5.2.

C.07 · Section summary

Inference optimisation in three layers

A useful way to hold the whole chapter: techniques act on the model, on the system that serves it, or on the request itself. Stacking across all three is what has driven the fall in cost per token.

LayerTechniquesWhat it buysWhat it costs or risks
The modelQuantisation, distillation, grouped-query and latent attention, mixture-of-experts routingLess memory per weight and per token, and fewer weights touched per tokenSome accuracy, unevenly across tasks. Architecture choices are fixed before training.
The systemPaged attention, continuous batching, chunked prefill, speculative decoding, splitting prefill from decode across machinesMuch higher utilisation of the same hardware, and a better latency-throughput frontierEngineering complexity. Several techniques help at small batch sizes and hurt at large ones.
The requestPrefix and prompt caching, shorter contexts, controlling how long the model thinksAvoided work, and direct control over what each request costsRequires discipline in how prompts are built. Shared caches raise questions about isolation.
The one fact to carry into chapter 04

None of this changes what the model knows. It changes how much capability a given quantity of hardware can deliver, and how cheaply. That is precisely the quantity that compute-based policy instruments assume is stable.
